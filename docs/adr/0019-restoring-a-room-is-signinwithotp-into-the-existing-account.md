# Restoring a Room is signInWithOtp into the existing account, not updateUser

ADR-0018 made **Claim** a UUID-preserving `updateUser({ email })` on the anonymous User: ownership becomes durable with zero data migration, but there is no way to get a Claimed Room back on a *second* device. There, the browser boots as a brand-new anonymous User (its own UUID + an empty "Untitled" Room from `ensureInitialRoom`). **Restore** — the Notebook's "Restore My Room" page — fills that gap.

We decided **Restore is `supabase.auth.signInWithOtp({ email, options: { shouldCreateUser: false } })`** — a magic link that signs the device *into* the existing permanent account, swapping the browser's session from the throwaway anonymous UUID to the permanent account's UUID. This is the exact option ADR-0018 **rejected** for Claim, and that rejection still stands *for Claim*. For Restore it is the correct one: there is no anonymous data we want to keep being orphaned — the User is re-entering an account that already owns its Rooms.

## Considered Options

- **`updateUser({ email })` (the Claim mechanic)** — rejected: the email already identifies a permanent account. You cannot promote a second anonymous User into an email that is already taken, and `updateUser` cannot merge two existing identities.
- **`linkIdentity({ email })`** — rejected: same reason. The identity already exists and is not free to attach to the current anonymous UUID; it would fork data across two UUIDs.
- **`signInWithOtp` into the existing account (chosen)** — signs the device into the permanent account. The anonymous session is replaced. No merge, no migration: the permanent account already owns the Rooms being reopened.

## Consequences

- **Session swap, not promotion.** The device leaves its anonymous identity; that identity's guest Rooms become unreachable from this device. `shouldCreateUser: false` ensures a mistyped or never-Claimed email does **not** silently mint an empty permanent account; the UI copy stays neutral ("if a room is registered to this email, a letter is on its way") so it never leaks whether an email exists.
- **Guest cleanup is consented and eager.** Restore warns that continuing clears **all** guest Rooms on this device. On accept we hard-delete every Room owned by the anonymous User — a single `delete from rooms where owner_id = <anon>` that cascades to surfaces → notes/annotations → strokes via the existing `ON DELETE CASCADE` foreign keys. We send the magic link **first** and delete only after `signInWithOtp` resolves, so a failed send never destroys data. The delete must run while still anonymous: RLS (`auth.uid() = owner_id`) only lets the anon User delete its own rows, and after the swap it is impossible. No schema migration is required — only a repository `deleteRoom`/`deleteRoomsForOwner`.
- **Telling the return apart from a Claim return.** The magic-link return fires `onAuthStateChange` just like Claim, so the existing handler (`email && !is_anonymous` → `claimStatus = "claimed"`) would wrongly pop the ownership certificate. We persist an **auth-intent flag** before sending the link and branch on return: Claim (UUID unchanged) → certificate; Restore (new UUID) → reload the now-permanent User's Rooms and open the selection page. The flag is cleared after handling.
- **Redirect target differs from Claim.** Claim returns to `/room/:id` (the same UUID owns it). Restore cannot know the target Room on a fresh device, so `emailRedirectTo` points at the app origin; the restore-return handler lists Rooms and routes — auto-flying in when exactly one exists, else showing the "Your Rooms" selection page (or a "no room found" page on zero).
- **No new "environment" persistence.** Notes, layout (Pin `(surface_id, u, v)`), Camera pose (`camera_yaw/pitch/distance`), and Room name already persist and reload through `loadRoom`. Weather and City are fixed, non-persisted set-dressing (ADR-0015), so there is no per-Room environment state to restore despite the brief's wording.
- **Same-device assumption.** As with ADR-0018's `emailRedirectTo`, the link is expected to be opened on the device that requested it (the `localStorage` intent flag lives there). Opening the link on a third, unrelated device is out of scope for v2.
- **Deployment** is unchanged from ADR-0018 (Anonymous sign-ins + email auth). `signInWithOtp` must be permitted; a project-wide "disable new user signups" setting is compatible with `shouldCreateUser: false`.
