# Annotations Are a First-Class Content Type Alongside Notes

The "draw on walls" feature adds a second content type to a Surface: an **Annotation** — a freehand vector drawing distinct from a **Note**. A Surface now holds zero or more Notes *and* zero or more Annotations; the two share the same `(u, v)` coordinate system but live in separate tables (`annotations` and `annotation_strokes`) with their own rendering and editing pipelines.

We chose a **separate entity** rather than collapsing Notes and Annotations into one "Surface content" table behind a discriminator. The two have almost no shape in common: a Note is one record with a text body, dimensions in centimetres, a single colour, an attachment style, and a cloth-simulated mesh; an Annotation is a collection of Strokes, each Stroke a pressure-weighted polyline in `(u, v)` space, with no centimetre dimensions, no body, no cloth simulation, no attachment. Forcing a `kind` column would mean half the columns are null for half the rows, and the editing UI for "edit Note text" has nothing in common with "draw a pen Stroke". Two clean tables are cheaper than one polymorphic one.

We chose **vector Strokes** over a baked raster texture per Surface. The Camera in v2 freely rotates and dollies; the user can fly close to a wall and inspect a doodle from a few centimetres away. A baked texture either has to be enormous (gigabytes-per-wall at retina-close resolution) or it pixelates the moment the Camera approaches. Vector Strokes render crisply at any zoom, support per-Stroke undo / redo, and let a future feature recolour or move Strokes individually. The cost is a stroke-tessellation step every frame for visible Annotations — but Annotations sleep when off-screen exactly like Notes do, and the stroke count per Surface stays low in practice.

We chose to **reuse the Palette** for stroke colour. The Palette's job is to keep the aesthetic coherent across content types; pen colours pulling from the same hue set as Note backgrounds means a doodle in `peach` reads as the same warm peach as the Notes nearby. There is no free colour picker — same restriction as Notes.

We chose a **mode-based input model**: a small tool palette in the chrome offers Note / Pen / Eraser as mutually exclusive modes. Clicking an empty wall in Pen mode begins a Stroke; clicking in Note mode creates a Note. The mode is global per User session and resets to "Note" on Room open. Modes are explicit because the Camera/Room is already busy with multiple gestures (orbit drag, wheel zoom, click-to-focus, drag-Notes-across-Surfaces) and overloading a fifth gesture onto the same pointer would be brittle.

The accepted cost: the v2 schema migration that introduced Notes (ADR-0011) now needs a sibling migration for `annotations` and `annotation_strokes`. The Surface picker UI grows a tool palette. Focus mode (ADR-0009) doesn't apply to Annotations — there is no "edit Annotation" focus state; editing is line-by-line via the Pen tool while the Camera is in its normal orbit pose. This is a deliberate scope choice and matches how Procreate / Figma actually work.

The reversal cost is real but bounded. If Annotations don't earn their seat, the Pen tool hides, the tables stay, and the data is dormant — no migration needed to roll back functionality, only to roll back data, and the data is per-User.
